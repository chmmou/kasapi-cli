# kasapi-cli Vertical Slice

Use this skill when adding a new KAS API endpoint to kasapi-cli. It captures the recurring slice anatomy and the order of operations; it deliberately avoids duplicating content already documented in `CLAUDE.md`, `CONTRIBUTING.md`, and the `docs/go/` references — those remain authoritative.

## Trigger

Apply when the user asks to:

- implement the next endpoint from the v0.2.0 backlog,
- add support for a specific `<kas_action>` (e.g. `add_mailforward`, `get_mailinglists`),
- start a new module (e.g. DDNS, Verzeichnisschutz, Samba) that does not yet have an `internal/<module>/` package.

Do **not** apply for: bug fixes inside an existing module, doc-only changes, refactors that touch multiple modules, or tooling/CI work.

## Pre-flight

Before writing any code:

1. **Read the KAS documentation page** for the action: `https://kasapi.kasserver.com/dokumentation/phpdoc/files/<kas_action>-inc.html`. Note the request fields, response fields (including their nesting), and documented fault conditions. Treat this page as the contract for the request shape.
2. **Capture a real KAS response** (or ask the user for one) and commit it under `testdata/<module>/<kas_action>_response_<status>[_<variant>].xml`. The filename convention is documented in `CLAUDE.md` — follow it exactly. **Redact secrets** before committing: session IDs, customer login names, mail addresses, IP addresses, anything identifying.
3. The fixture is the contract for the response shape — when a mapping test later disagrees with the fixture, suspect the mapping first.

## Slice Anatomy

A complete slice touches these files. Paths are concrete; if a target file does not yet exist, create it.

| File | Role |
|---|---|
| `testdata/<module>/<kas_action>_response_success.xml` | success fixture (mandatory) |
| `testdata/<module>/<kas_action>_response_failed_<reason>.xml` | at least one fault fixture (mandatory) |
| `internal/<module>/<module>.go` | request + response structs, `Decode<Thing>` mapper (SOAP `ns2:Map`/`Array` → domain type), and a per-package `Caller` interface so tests do not need network setup |
| `internal/<module>/<module>_test.go` | mapping tests against the fixtures (success + each fault variant) |
| `internal/<module>/<module>.go` (or a dedicated `client.go` in the same package) | accessor on the per-package `*Client`, e.g. `(c *Client) Get(ctx, name) (Thing, error)` — it dispatches via the `Caller` and runs the mapper. The transport-level `KasRequestParams` envelope is filled centrally by `internal/soap/request.go`; module code passes plain `map[string]any` parameters to `Caller.Call` |
| `internal/cli/<module>.go` | Cobra subcommand with flags, table/JSON output via the existing helpers |
| `cmd/kasapi-cli/main.go` | one-line registration of the new subcommand — nothing else |
| `docs/cli/**` | regenerated by `make docs`; never hand-edited |
| `CHANGELOG.md` | one English entry under `[Unreleased]/Added` |
| `docs/usage/<module>.md` | optional, only when the CLI help is not enough |

## Order of Operations

Strict order — earlier steps gate later ones:

1. **Fixture** committed (success + at least one fault).
2. **Mapping** + mapping test — drive the mapping red-to-green against the fixture.
3. **Client accessor** on the module's own `*Client` (in the module package — either inline in `<module>.go` or in a dedicated `client.go`), dispatching via the per-package `Caller` interface and running the mapper.
4. **CLI subcommand** with flags and output formatting.
5. **`make docs && git add docs/cli/`** — the `docs sync` CI job will fail otherwise.
6. **CHANGELOG** entry.

This ordering ensures the mapping is already green before any CLI fluff is written, and that `docs/cli/` never lags the command tree.

## Layering Discipline

Refer to `docs/go/ARCHITECTURE.md` for the full clean-architecture layering. The slice-relevant rules:

- No SOAP/XML imports in `internal/<module>/` — the domain layer must not know how its types are transported.
- No `cobra`/CLI imports in `internal/<module>/`.
- Domain types carry no `xml:"..."` struct tags — those live on the transport-layer DTOs that the mapper consumes.

## Hand-off to the companion skills

- For branch creation, signed commits, FF-push merge, and branch cleanup: defer to **`kasapi-cli-git-workflow`**. Default branch name for a slice: `feature/<module>-<action>` (e.g. `feature/mailforward-add`).
- For the review pass after the first green CI run, and for the re-review cycle after corrections: defer to **`kasapi-cli-code-review`**.

## Acceptance Criteria

A slice is done when **all** of these hold:

- All CI gates green (`lint & test`, `docs sync`, `goreleaser config check`, `govulncheck`, CodeQL).
- Mapping tests cover success and at least one documented fault variant.
- `make docs` produces no diff against the checked-in `docs/cli/`.
- `CHANGELOG.md` has an `[Unreleased]/Added` entry in English, of the form `add <kas_action> read support` (or `add <kas_action> write support` once the v0.2.0 write phase begins).
- The new subcommand is visible in `kasapi-cli --help` and `kasapi-cli <module> --help`.
- The PR is FF-merged into `main` with the maintainer's signature preserved (see `kasapi-cli-git-workflow`).

## Deliberately not included

These are documented elsewhere; do not duplicate into the slice flow:

- Go style rules — see `docs/go/STYLE_GUIDE.md`.
- Linter set + CI gate — see `docs/go/LINTING.md`.
- Signed-commit + FF-push mechanics — see `kasapi-cli-git-workflow`.
- Review classification (Blocker/Should/Nice-to-have) — see `kasapi-cli-code-review`.
- Language conventions for repo artefacts — already in scope via the user's standing instructions.
